## Context

The monorepo currently has:
- `apps/gateway` — NestJS app with MikroORM/PostgreSQL wired, no GraphQL yet
- `libs/db` — shared MikroORM config factory (`createMikroOrmOptions`) + `DbModule`
- `docker-compose.yaml` — PostgreSQL running on port 5432

Three reference files in `tmp/` define the target patterns:
- `creates-better-auth-instance.ts` — `initAuth()` factory initialising Better Auth with email/password, social providers, and plugins (organization, twoFactor, magicLink, multiSession, admin, openAPI, customSession)
- `exposes-better-auth.ts` — `BetterAuthFactory` NestJS provider + `ConfigurableModuleBuilder` (forRoot async pattern)
- `integrate-better-auth-with-mikroorm.ts` — Kysely dialect created from MikroORM `SqlEntityManager`, wrapped with `CamelCasePlugin` + `MikroKyselyPlugin`, fed into `kyselyAdapter` for Better Auth

The architecture is Apollo Federation: a lightweight gateway (`apps/gateway`) composes multiple subgraphs. `apps/users-subgraph` is the first subgraph — it owns auth identity.

## Goals / Non-Goals

**Goals:**
- Create `apps/users-subgraph`: NestJS app, Apollo Federation subgraph, schema-first GraphQL
- Create `libs/auth`: Better Auth NestJS module with Kysely/MikroORM adapter
- Create `libs/users`: MikroORM entities for Better Auth core tables
- Expose `me: User` query via CQRS — resolver → `GetMeQuery` → handler reads session from Better Auth
- Mount Better Auth REST handler at `/auth/**` in users-subgraph
- Shared GraphQL context: extract `sessionId` from cookie, pass into every resolver

**Non-Goals:**
- Organization / team plugins (out of scope for this change — simple email+password + social)
- Gateway federation stitching (gateway will be wired in a separate change)
- Frontend auth client integration
- Email sending (mailing service stubbed out / omitted for now)
- Two-factor auth, magic link (plugins listed in reference but not activated yet)

## Decisions

### D1 — Schema-first GraphQL with `@nestjs/graphql` (federation mode)

`GraphQLModule.forRoot<ApolloFederationDriverConfig>` with `ApolloFederationDriver` and `autoSchemaFile: false` (schema-first). SDL is in `schema.graphql`, types generated by `@graphql-codegen/typescript` + `@graphql-codegen/typescript-resolvers`. Alternative (code-first) rejected because the project explicitly mandates schema-first.

### D2 — Better Auth Kysely adapter bridged via MikroORM

Better Auth requires a database adapter. The reference files use `kyselyAdapter` from `@better-auth/kysely-adapter` with a Kysely instance created from MikroORM's `SqlEntityManager.getConnection().createKyselyDialect()`. This keeps a single DB connection pool and lets MikroORM manage migrations while Better Auth reads/writes through Kysely. Alternative (Better Auth's own `pg` adapter) rejected because it would create a second independent connection pool.

### D3 — `libs/auth` as a NestJS `ConfigurableModuleBuilder` module

Mirrors `exposes-better-auth.ts` exactly: `BetterAuthModule.forRootAsync({ mailingService: ... })`. The `BETTER_AUTH_TOKEN` provider holds the `BetterAuth` instance. The `AuthDatabaseKyselyFactory` and `BetterAuthDatabaseAdapterFactory` are internal providers. This encapsulates all auth wiring in one importable lib. Alternative (inline in app module) rejected because other future subgraphs may also need auth.

### D4 — CQRS for the `me` resolver

`MeResolver` dispatches `GetMeQuery(sessionId)` via `QueryBus`. `GetMeQueryHandler` calls `BetterAuth.api.getSession({ headers })` and returns `null` if no session. CQRS separates the resolver (transport layer) from the use-case (application layer), aligning with DDD. Alternative (direct service call in resolver) rejected per architecture decision in project context.

### D5 — Cookie-based session transport, shared context

The GraphQL context factory (`context` option in `GraphQLModule`) extracts the `better-auth.session_token` cookie from the incoming HTTP request and puts `sessionId` in the context. Resolvers receive it typed via a `GqlContext` interface. The gateway will later forward this cookie to subgraphs via Apollo Router headers.

### D6 — `libs/users` for MikroORM entities

Better Auth core tables (`user`, `session`, `account`, `verification`) are MikroORM entities in `libs/users`. They follow Better Auth's expected column names (snake_case). MikroORM migrations (via CLI) generate the DDL. No custom repositories in this change — entities are raw data structures only.

### D8 — WordPress identity bridge via Apollo Federation using email as shared reference key

**Constraint**: The JavaScript layer must never access the WordPress MySQL database directly, nor call the WordPress REST API from our services. All WordPress data access must go through Apollo Federation.

**Consequence**: The `wordpressUserId` integer cannot be stored in the Better Auth `user` row at signup — there is no permissible channel to retrieve it without hitting the REST API or MySQL directly.

**Federation-native approach**: The `User` type in `users-subgraph` declares a single `@key(fields: "id")` and exposes `email` as a non-key field. The WPGraphQL Federation subgraph (WordPress side) extends the `User` type by matching on `email` — WordPress users are looked up by their email address within the WPGraphQL reference resolver. The Apollo Gateway/Router stitches the two representations together at query time without any cross-system call originating from our Node.js code.

**SDL impact**: `User` SDL is `type User @key(fields: "id") { id: ID! email: String! name: String! }` — no `wordpressUserId` field, no second `@key`. The WPGraphQL side declares `extend type User @key(fields: "id") { id: ID! @external ... }` or resolves by email depending on the WPGraphQL Federation plugin's configuration.

**Accepted trade-off**: If a user changes their email in Better Auth but not in WordPress (or vice versa), the federation link silently breaks. This is accepted because the alternative (REST API or direct DB calls) violates the architecture constraint. Email-change workflows must keep both systems in sync (out of scope for this change).

### D10 — Rspack replaces Webpack for all NestJS apps

Webpack class name minification breaks MikroORM v7 entity schema discovery (`defineEntity` binds to class constructor; webpack silently strips the `.name` property). Rspack preserves class names by default with `output.iife: false` (Node.js target) and is the Nx-recommended bundler for NestJS apps in the monorepo.

All apps that use MikroORM entities (`apps/users-subgraph`, `apps/migrator`) must be migrated from webpack (`@nx/webpack/app-plugin`) to Rspack (`@nx/rspack/app-plugin`). The gateway does not have entities yet so can be migrated later.

### D11 — Migrator has a dedicated MigrationModule with MigrationService

The migrator app should not wire MikroORM directly in `AppModule`. Instead:
- `apps/migrator/src/migration/migration.module.ts` — imports `MikroOrmModule.forRootAsync(...)` with all entity schemas passed through `entities` array
- `apps/migrator/src/migration/migration.service.ts` — `OnApplicationBootstrap` hook that calls `orm.getMigrator().up()` then `process.exit(0)`
- `apps/migrator/src/app/app.module.ts` — imports only `DbModule` and `MigrationModule`

This separates DB connection config (AppModule) from migration execution logic (MigrationModule), matching the single-responsibility pattern.

### D9 — DDD sub-libs inside libs/users to avoid federation circular dependencies

`libs/users` is split into four co-located Nx projects inside the same folder:

```
libs/users/
  src/              ← main lib (@desafio/users) — federation entry: re-exports, @key resolver stubs
  domain/           ← @desafio/users-domain — pure TS User interface, no framework deps
  application/      ← @desafio/users-application — CQRS GetMeQuery + handler
  infrastructure/   ← @desafio/users-infrastructure — MikroORM entities
```

**Dependency direction (enforced by Nx boundaries):**
- `infrastructure → domain` (entities implement domain interfaces)
- `application → domain` (handlers work with domain types)
- `users (main) → application + infrastructure` (federation surface re-exports)
- Sub-libs never import from the main lib or from each other except via the `domain` layer

This eliminates the federation circular dep pattern where a resolver imports an ORM entity which imports a GraphQL type which imports the resolver.

Alternative (flat `libs/users/src/`) rejected because it makes the dep boundary implicit and unenforceable; circular imports emerge silently as the lib grows.

### D7 — Simple email/password + Google OAuth only

The reference `initAuth` factory has many plugins. For this change only email/password (sign-in only, no self-signup) and optional Google OAuth are activated. Plugin expansion is a separate change.

## Risks / Trade-offs

- **`createKyselyDialect` availability**: MikroORM v7 + PostgreSQL driver exposes this on `SqlEntityManager`. If the method changes in future MikroORM versions this adapter breaks. Mitigation: pin `@mikro-orm/postgresql` version.
- **Better Auth schema vs MikroORM migration**: Better Auth generates its own migration SQL (`pnpm better-auth generate`). The generated SQL must be reconciled with MikroORM migrations. Mitigation: run `better-auth generate` first, paste output into a MikroORM migration file, let MikroORM own the migration lifecycle.
- **Federation schema SDL validation**: Apollo Federation requires specific directives (`@key`, `@external`, etc.) in the SDL. Errors surface only at subgraph startup. Mitigation: use `@apollo/subgraph` `buildSubgraphSchema` and validate SDL in CI.
- **Cookie forwarding in federation**: The gateway must forward the `Cookie` header to subgraphs. This is a gateway concern, but must be kept in mind when designing the context factory. Mitigation: document in users-subgraph that it expects `cookie` header from the gateway.
- **Email-change federation break**: If a user's email changes in Better Auth but not in WordPress (or vice versa), the WPGraphQL Federation link breaks silently. Mitigation: email-change flows must be coordinated across both systems; out of scope for this change.

## Migration Plan

1. Scaffold `apps/users-subgraph` and `libs/auth`, `libs/users` via Nx generators
2. Install new dependencies
3. Define `schema.graphql` SDL
4. Implement MikroORM entities and run `pnpm mikro-orm migration:create`
5. Run `pnpm better-auth generate` — paste generated SQL into the migration
6. Run `pnpm mikro-orm migration:up`
7. Implement `BetterAuthModule` in `libs/auth`
8. Implement CQRS `GetMeQuery` + handler
9. Wire `MeResolver` + GraphQL context factory
10. Test `pnpm nx serve users-subgraph` and call `query { me { id email } }`

Rollback: `pnpm mikro-orm migration:down`, remove app and libs.
